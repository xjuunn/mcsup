# MCSUP 并发与性能规范

来自 `AGENTS.md`。

涉及并发、性能、IO 或任务取消时查阅。

---

# 并发设计

区分 Concurrency（并发）与 Parallelism（并行）。设计时关注 Tokio、async/await、
Send / Sync、Mutex / RwLock、channels、backpressure、cancellation、timeout、
task lifecycle。

禁止 `Arc<Mutex<Everything>>`，禁止用全局锁解决一切，锁粒度尽量小。禁止持锁做
网络请求或长等待：正确顺序是读取状态 → 释放锁 → 执行 IO → 重新更新状态。

# 性能原则

以生产级性能为目标，优化必须基于实际测量而非感觉。关注 CPU、内存、IO、磁盘、
网络、锁竞争、分配、拷贝、序列化、哈希、延迟、吞吐。高风险路径：

- Backup：大文件、Hash、去重、磁盘 IO、并行哈希、Snapshot、GC
- File Transfer：Streaming、Chunk、Checksum、压缩、带宽、内存、Backpressure
- RPC：延迟、序列化、Streaming、连接复用、压缩、并发
- Server Management：进程 IO、日志流、事件分发、状态更新

# 资源生命周期

Process / File / Socket / Connection / Task / Channel / Lock / 临时文件 /
Backup 都必须明确 Create → Use → Cancel → Timeout → Failure → Cleanup，
尤其是 spawn、文件、网络、备份、临时目录，不能泄漏。

# Cancellation

Backup / Download / Upload / File Copy / Restore / RPC Streaming / Log
Streaming 等长任务必须支持 CancellationToken，取消后正确清理资源。

# Timeout

HTTP / RPC / Provider / File Transfer / Agent / Database 等外部 IO 必须有
Timeout，不能无限等待。

# 网络设计

网络操作必须考虑 Timeout、Retry、Backoff、Cancellation、连接复用、错误分类、
Rate Limit。Retry 必须区分可重试与不可重试错误，禁止对所有错误无限 Retry。

## 下载并发

下载有三层各自独立、互不叠加的并发控制，缺一层都会失控：

| 层 | 位置 | 作用 |
| --- | --- | --- |
| 批量并发 | `download-concurrency`，缺省 24 | 同时在途的**文件**数 |
| 分段并发 | `file` 的 `SEGMENT_CONCURRENCY`，128 | 单个大文件内部同时在途的**段**数 |
| 在途上限 | `download-inflight`，缺省 256 | 上面两层乘起来之后，真实同时在途的**连接**数 |

前两层各自有界、乘起来没有界：24 个文件各切 128 段会想抽 3072 条连接，超过多数
家庭带宽与上游对单 IP 的容忍度。第三层就是这道闸门，取值 `None` 表示不限（自定义
来源时的既有行为）。

实测结论（同一个 Modrinth CDN `cdn.modrinth.com`，跨境链路，2026-11）：单连接被
限速在约 **45 KiB/s**，且聚合吞吐随**在途连接数**近似线性增长，直到约 15 MiB/s
的单节点容量——不是「8 路到顶」，而是「每加一条连接就多约 45 KiB/s」：

| 在途连接数 | 8 | 24 | 48 | 96 | 128 | 192 | 256 | 384 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 单文件 MiB/s | 0.42 | 1.10 | 2.0 | 4.2 | 5.0 | 9.1 | 11.5 | 16.6 |

高并发（256 乃至 384 连接）实测不触发上游 429 / 5xx。据此：

- 取回 `.mrpack`（单文件）只走分段并发：24 段约 1.0 MiB/s，128 段约 7.5 MiB/s。
- 布置清单（109 文件 / 594 MiB）走三层：基线 `8/24/48` 约 1.4 MiB/s，调成
  `24/128/256` 约 8 MiB/s。

缺省值因此定在实测增益明显、又不顶到上游限流的量级：批量 24、分段 128、在途 256。
链路更宽裕或更窄时由用户经 `mcsup config set` 调整，不把缺省顶到最大值。另注意
同一 CDN 的不同 anycast 节点单连接速率呈双峰（多数节点约 45 KiB/s，个别节点偶发
30+ MiB/s），且不稳定、无法可靠固化——把吞吐押在并发叠加而非节点选择上。

已知大小且低于分段阈值（`file` 的 `MIN_SEGMENTED_SIZE`，2 MiB）的小文件不再先发
HEAD 探测：`expected_size` 已能判定它不会分段，单流也不需要范围能力，省一次往返
是纯收益。阈值从 8 MiB 降到 2 MiB、单段从 2 MiB 降到 1 MiB 的原因实测很直接：同一
CDN 节点单连接只有 20–45 KiB/s，一个 6.5 MiB 的中等文件在 8 MiB 阈值下只能单流，
要几分钟；降到 2 MiB 后它切成 6 段，尾部耗时缩短到约 1/6。批量里的文件大小分布
长尾明显，卡在尾部的一两个中等文件往往就是「明明快下完了却又等很久」的全部原因。

批量下载的**顺序**同样影响观感与总耗时：文件按体积**降序**下发（最长处理时间优先，
LPT 调度）。大文件先启动、占满批量并发和最多的墙钟时间，小文件补尾部；否则按清单
原始顺序下载时，大文件若排在末尾会拖着尾段、在途连接数一路衰减，进度条「越下越慢」——降序在观感上更平稳，也最小化整批完成时间。

整批进度的记账按**高水位**：单文件回调不是单调的（分段失败会退还该段字节、换源与
「分段回退单流」都从 0 重来），只把超过历史最高值的部分计入，并以上限（清单声明
大小）封顶。否则退款后重传的同一段字节会被再算一遍，进度越过总量（实测显示
`88.93 MiB/88.41 MiB`），速度也随之虚高。第二阶段「清单哈希过期后回源重下」的
字节已在上一步计入，不再向进度条汇报，避免整包位置倒退。

## 断点续传

分段下载的临时文件路径是**确定**的（`.<名字>.<大小>.part`），落在目标文件同级
目录；每写完一段就在 `.<名字>.<大小>.part.marks` 追加一行段序号。于是同一目标的
重试、以及 Ctrl-C 之后的重新运行，都只补没写完的段，而不是从头再来——对一个
0.06 MiB/s 链路上的 200 MiB 文件，这决定了中断一次是浪费一分钟还是一小时。

三条约束保证它不会把错内容拼进去：

- 残片长度与上游不符即整份重下（换了版本或上次写坏）
- 段记录读不懂即当作没有进度（它只是加速手段，不该让下载失败）
- 收尾仍按清单声明的校验和整体校验，续传不会绕过它

校验失败（`ChecksumMismatch` / `SizeMismatch`）时才丢弃残片：那些字节已被证明
不是要的内容。其余失败（瞬态网络、超时、用户取消）一律保留残片，因为续传的
全部意义正在于这些场景。
