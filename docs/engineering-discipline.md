# MCSUP 工程纪律

来自 `AGENTS.md`。

新建模块、改动已有代码、遇到设计缺陷时查阅。

---

# 不要一次创建所有模块

最终架构不代表第一天就建所有目录。只有当真实架构边界出现时才创建新模块，禁止
为「未来可能使用」建十几个空模块。流程：需求出现 → 确认职责边界 → 确认是否需要
独立模块 → 创建 → 编写测试 → 实现。只有几十行代码且没有独立边界的，不单独拆
模块。

# 修改现有代码之前

不允许直接修改。先理解调用链、依赖关系、状态模型、错误模型与测试，优先查看
Cargo.toml、模块结构、相关 Trait / Service / Test，理解现有设计后再改。

# 禁止无意义重构

用户要求「增加功能 A」，就不能顺便重写 Service、重构 Storage、重写 Runtime、
更换异步框架或数据库、重命名几十个模块，除非当前任务确实要求。遵循最小必要
修改原则。

# 发现架构问题

不要直接大规模重构。流程：发现问题 → 分析原因 → 说明影响 → 提出方案 → 选择
最小合理改动 → 增加测试 → 迁移 → 验证。不能为「架构更漂亮」而大规模重构。

# 架构修改规则

需要修改架构时先确认：为什么现有架构无法满足、边界在哪里、新的依赖方向是
什么、会影响哪些模块、如何迁移、如何测试、如何保证兼容。架构调整必须有明确
理由。
