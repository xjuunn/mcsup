# AI 协助开发细则

本项目由人写代码、AI 协助。本文件是细则，AGENTS.md 只保留指针。

三条底线，任何类型都适用：

```
禁止 → 未经要求就动手改代码，只报告问题
禁止 → 把风格问题说成阻断级风险来凑数
禁止 → 用 check.sh 通过来证明业务逻辑正确
禁止 → 未经同意就新增依赖
```

提问分三类。只执行对应类型的动作，不要跨类型。

| 类型 | 是否跑 check.sh | 是否读改动 |
| --- | --- | --- |
| 方案类 | 否 | 否 |
| 代码类 | 否 | 是 |
| 审查类 | 是 | 是 |

## 方案类

触发：「接下来做什么」「怎么设计」「该选哪个」。

1. 读 `docs/architecture.md` 判断任务是否落在现有架构内
2. 读相关 `docs/` 细则
3. 给出 2-4 个方案，列出关键取舍
4. 明确推荐一个，说明理由

```
禁止 → 跑 check.sh 或任何构建命令
禁止 → 读 git diff
```

还没写代码，跑了也没有可测的对象。

不确定的地方直接问，不要替用户假设。

## 代码类

触发：「这段代码怎么写」「帮我写 X」。

1. 读 `git status` / `git diff`，看用户正在写什么
2. 在他的基础上回答，不要凭空给通用示例
3. 按级别列出问题，逐条给出改法

```
禁止 → 跑 check.sh
```

用户刚写完，通常还没写完。代码类只回答问题，不做门禁。

不要整段重写他的代码，除非他明确要求。

### 依赖选择

发现成熟的库能大幅简化当前任务时，主动提出，先问再装。四条信息缺一不可：

```
库名与用途
替代多少手写代码
是否降低缺陷面
许可证与传递依赖规模
```

收益说不清就不要提——「减少手写代码」必须落到具体功能上，不能是
「代码更简洁」这种无法验证的说法。

```
禁止 → 用户没同意就写进 Cargo.toml
```

### 封装优先

先问这段逻辑将来会不会变。会变就先抽取边界，再写实现。

```
重复出现两次 → 抽取
已有 port 但直接调了实现 → 补 trait 实现，走 port
跨层调用 → 移到正确层，不要就地打补丁
```

```
禁止 → 为「将来可能用到」提前抽象
禁止 → 只有一个调用方却建 trait
```

判断依据是「已经存在的变化压力」，不是「可能变化」。没有第二个调用方、
没有第二个实现，就不要抽象——过度封装的代价是所有调用点都要穿过无意义的间接层。

| 级别 | 含义 | 处理 |
| --- | --- | --- |
| 阻断 | 违反架构规则、必然出错、缺测试 | 必须说明，指出所属层 |
| 应改 | 有隐患但当前不会出错 | 说明触发条件 |
| 建议 | 可读性、命名、风格 | 简短列出即可 |

没有阻断级问题就直说。

## 审查类

触发：「这段对不对」「能提交吗」「帮我 review」。

三步缺一不可：

```
1. scripts/check.sh                    跑测试
2. sh scripts/check-architecture.sh    查架构
3. 阅读改动，查漏洞                    逻辑、并发、错误处理、边界
```

第 3 步的漏洞重点：

```
错误处理吞掉了失败
并发下存在竞态或死锁
外部输入未校验
资源泄漏
失败路径不可恢复
```

完成后明确说结论：能否提交，有无阻断项。
